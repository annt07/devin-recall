# Recall Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use godmode:subagent-driven-development (recommended) or godmode:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Recall, an automatic, per-repo, versioned wiki memory for Devin CLI.

**Architecture:** One Python package. The Store module (pages, raw records, index, log) sits on History, the only module that runs git. The Gate verifies each page write. Two adapters sit on the same Store: the hook adapter (scripts that Devin starts) and the MCP adapter (tools that the agent calls). The Session Reader is a read-only adapter for the Devin `sessions.db`.

**Tech Stack:** Python 3.11+, uv, PyYAML, `mcp` SDK (FastMCP), sqlite3 FTS5, git CLI, pytest.

**Spec:** `docs/godmode/specs/2026-10-30-recall-design.md`

## Global Constraints

- Recall never writes, changes, moves or removes Devin internal data. Open `sessions.db` only with the URI `mode=ro`. Open other Devin files only in read mode.
- Recall writes only in `<repo>/.devin/recall/` and in its local data folder (`%LOCALAPPDATA%\devin-recall\<key>`, or `RECALL_LOCAL_DIR` in tests).
- A hook never breaks Devin. Each hook catches all exceptions, writes them to `errors.log` in the local data folder, and exits 0.
- Write all text files with `newline="\n"` and UTF-8.
- Git commits in the store use `-c user.name=Recall -c user.email=recall@localhost -c core.autocrlf=false`. Never change any git config.
- The user never runs a command. Hooks and MCP tools start all operations. The agent runs `recall install` one time.
- Limits: page ≤ 800 tokens (chars/4), index ~1.5k tokens, injection ≤ 3 pages and ≤ 10,000 chars for each prompt, raw record ≤ 20,000 chars, Seed 90 days and 3 sessions for each SessionStart.
- Test command: `uv run pytest -q`. Run from the repo root.

## Review Focus

1. A hook `session_id` that is not in `sessions.db` (the probe can show that the formats are different). Expected: the Session Reader uses the most recent session of the repo.
2. Two Devin sessions on the same repo at the same time. Expected: no corrupt git state, the second writer skips its commit and the next commit includes its files.
3. A Stop hook that blocks again and again. Expected: maximum one block in 15 minutes, and no block after an ingest.
4. The agent writes into `.devin/recall/` with `exec` (shell) and not with `write`/`edit`. Expected: v1 does not block it. The Skill forbids it.
5. Paths with spaces and OneDrive locks (the workspace path contains spaces). Expected: all subprocess calls use argument lists and no shell.

Commit scope: `History.commit(..., paths=None)`. With `paths` (store-relative) only those paths are staged and committed (`git commit -- <paths>`); pending raw records never ride along. Owners: ingest → accepted pages, `index.md`, `log.md`, `consumed.txt`; lint → changed pages, `index.md`, `log.md`; capture → new raw files, `log.md`; seed → new raw files, `log.md`, `seed.json`; eval → `log.md`, `eval.md`. `paths=None` (`git add -A`) is only for init and revert. `Store.append_log(op, title, session, when=None)` writes one `## [stamp] op | title | session=` line.

Page front-matter keys: `type, title, summary, status, confidence, sources, anchors, updated, stale_since`. Ingest computes `anchors` (`git hash-object` of each code source) and `updated`. The agent does not send them.

Source forms: `raw/<file>.md`, `commit:<sha>`, `<repo path>[:a-b]`.

## Spec deviations (for plan review)

- The Gate duplicate guard uses Jaccard similarity (≥ 0.6) and not an FTS5 near-match, so that the result is deterministic and testable. FTS5 stays for retrieval.
- Stop saves `last_assistant_message` only when it blocks. If it saved on each Stop, each user turn would make a pending record and a block. SessionEnd captures the full messages from `sessions.db`.
- `index.md` is generated, so the lint rule "page not in index" is not necessary.
- `consumed.txt` is new. It records raw records that the agent read but that contained nothing durable, so that the drain rule can finish.
